# Decisions and deviations from AHEADLY_APP_SPEC.md

| # | Decision | Why |
|---|---|---|
| 1 | Pages are registered with `st.navigation` + `st.Page`; page scripts live in `aheadly/ui/views/` instead of a top-level `pages/` folder. | `st.navigation` is Streamlit's current multipage API and lets the sidebar show titles, icons and the unread-alert badge. A `pages/` folder next to `app.py` triggers Streamlit's legacy auto-navigation on first load, which clashed with it. |
| 2 | `accounts.balance` column added; `alerts.resolved` and `scenarios.result_json / saved_as_plan` added to the schema. | Current cash is an account balance, not a sum of history; alert resolution and saved plans are part of frame 6. |
| 3 | Prophet uses `growth="flat"` plus weekly seasonality and Colombian holidays; yearly seasonality only with 18+ months of data. | A bakery's cash flow is level + weekly pattern; extrapolating a trend from 12 noisy months made forecasts drift. |
| 4 | What-ifs reuse the sampled residual paths (cached per history) and only change the scheduled items. | Scenarios are instant and comparable: the only difference between baseline and scenario is the decision being tested. |
| 5 | Backtest (naive vs Prophet, MAE of daily net flow, last 28 days): seasonal_naive ≈ $138, Prophet ≈ $128 on the demo data (2026-11-09). | Course rule: never forecast without a naive baseline. Prophet wins narrowly; the naive model remains the fallback and the test-suite model. |
| 6 | Gemini is called through Google's OpenAI-compatible endpoint (`openai` package); Claude through the official `anthropic` SDK. | One neutral message format in `llm_client.py`; the OpenAI route is the one lecture 12 showed for Gemini. |
| 12 | Alert `weeks_ahead` counts to the lowest point and rounds to the nearest week; `top_outflows` covers the week ending at the lowest point. | The owner cares about when the real trouble lands; buying the oven this week already hovers around the line, which would otherwise read as "in 1 week". |
| 7 | Guardrail tolerance: exact match, ±1, or 1.5% rounding; integers ≤ 12 are treated as counts, not money. | "about $3,700" for 3,695 is honest rounding; "two bills" or "8 weeks" should not trip the check. |
| 8 | Offline `StubClient` picks a tool from keywords and fills templates; the same templates are the graceful fallback for real providers. | Demo and tests run with zero keys and exercise the real tool loop. |
| 9 | Plaid and QuickBooks connectors are scaffolds for this milestone (sign mapping implemented and tested; API calls pending). CSV import works. | Spec's "Use demo data must always work" is the MVP path; sandbox integrations are the next milestone. |
| 10 | Season peak modelled as two large café receivables three and eight days after the week-5 cluster. | Keeps the canonical story (shortfall ≈ -$4,000 in week 5; oven next month keeps cash above $3,000) on any run date in the first three weeks of a month. |
| 11 | `revenue_change` is modelled as one weekly adjustment line equal to the percentage of average weekly sales. | Simple and explainable; good enough for "what if sales drop 10%". |
| 13 | Brand theme lives in `.streamlit/config.toml` (Inter via `theme.fontFaces`, radii, colours, sidebar, `toolbarMode = "minimal"`); `ui/theme.py` only adds the cards, pills and hero Streamlit has no option for. | Native theme options reach every widget (inputs, nav, dataframes) without fragile CSS selectors, and the Deploy toolbar disappears from the demo. |
| 14 | Charts plot the **lowest balance of each week** (history and forecast) plus a "Today" anchor, instead of every day. | Daily balances saw-tooth with the weekly rhythm of sales and supplier payments and looked like noise; the weekly low is what alerts are about, the red dot always sits on the line, and the result reads like the mockups. |
| 15 | Default Gemini model is `gemini-3.5-flash-lite`; the client retries 429/503 up to twice, waiting as long as Google's RetryInfo asks (max 25 s, never for daily quotas); when the provider still fails, the chat answers from the offline planner plus templates with the "built directly from your numbers" note. Gemini 3 thought signatures are stored on `ToolCall.extra` and echoed back. | Measured on 2026-11-10 with a free key: `gemini-2.5-flash` returns 404 (retired for new users); `gemini-3.5-flash` takes 11 to 15 s per call and is capped at 20 requests per day; `3.5-flash-lite` answers in about 1 s per call with the same tool-calling quality. Without the signatures Gemini 3 rejects the second turn of every tool loop (400). |
| 16 | The file import accepts CSV and Excel, with bank-statement headers (Date / Description / Debit / Credit / Balance, English or Spanish) as well as the app's own columns. A sample export of Panadería La Esquina lives in `data/samples/` (regenerate with `uv run python -m scripts.make_sample_export`) and could be downloaded from the Accounts page (that button went away with the upload-only change, #20). | While Plaid and QuickBooks are pending, a client can upload what their bank already gives them. The sample doubles as the demo path for "connect your own data". |
| 17 | Each visitor (Streamlit session) gets their own App Core and an empty in-memory database (`PER_VISITOR_DATA=true`, the default); the forecast engine and LLM client stay shared. `PER_VISITOR_DATA=false` keeps the old single shared database file. | On the deployed app every visitor shared one database: a new visitor landed on whatever was loaded last, and importing a file while the demo was loaded mixed the transactions and summed the balances. Now every visit starts at onboarding, like a first-time user. A page refresh also starts over; saving data between visits comes later. |
| 18 | Every verdict uses three risk levels from `ForecastResult.risk_level`: act now (base case below the low cash line), keep an eye on it (only the worst case below it), safe (worst case stays above). Scenario summaries and `get_forecast` carry `risk_level` and the worst case; templates and the chat prompt (rule 8) use them. With no alert but a "watch" forecast, the dashboard shows a yellow "keep an eye on it" box instead of "healthy". | The app called a $2,000 purchase "safe" while its worst case fell to $479, below the $2,000 line, because only the base case was checked. A yellow dashboard box was chosen over a new low-severity alert type to keep the alerts table and its checks unchanged before Milestone 2. |
| 19 | `get_forecast` takes an optional `until` date; "next month" questions use the end of next month (offline planner and prompt rule 9). The "Lowest projected" card counts today's balance (`ForecastResult.lowest_with_today`). | "Will I have enough cash next month?" was answered with an 8-week lowest point in January, and the card showed a projected low above today's balance. |
| 20 | Onboarding is upload-only for Milestone 2: a bank statement (CSV or Excel; the current balance is read from its Balance column if not typed) plus an optional file of upcoming one-off payments and expected income (Date, Description, Amount). The Plaid/QuickBooks cards, "Use demo data" and the Maria photo are gone from the UI; `DemoConnector` stays for the tests. Imported files no longer default to Panadería La Esquina. | Team decision (2026-11-10): the product targets businesses that only have bank statements and their own Excel files. Regular payments are learned from the statement; listing them again in the upcoming file would count them twice, so that file is for one-off items only. The demo uses Maria's files, generated outside the repo. |
| 21 | Bank files: dates like 03/11/2026 are read day/month/year unless the file clearly uses month/day (a second number above 12); ISO dates as they are. Amounts accept 1.250,00 · 1,250.00 · $ 2.000 · (900,50); a single separator followed by exactly three digits is a thousands separator. Rows with an unreadable date or amount are skipped and counted, never turned into $0, and the owner is told. | The target clients are in Latin America. Before, "03/11/2026" became March 11 and "1.250,00" became $0 without any error. |
| 22 | Bank statements: when a statement ends before yesterday, the forecast starts the day after its last transaction (`AppCore.today`), and the app says so; a file listing the newest line first is turned around before anything else; a Balance column is checked line by line and breaks are reported; each transaction's id is a hash of its date, amount, description and balance (plus its order among identical lines), so a statement uploaded again, or two that overlap, never counts a line twice. | Roadmap 1.3. Forecasting from today with a statement that ends weeks earlier silently drops the days in between; the old ids used the row number, so the same line in two files looked like two transactions. |
| 23 | Streamlit's cached objects (forecast engine, LLM client, shared App Core) are keyed by a fingerprint of the app's code (`aheadly/version.py`), and `Settings` is read on every run instead of cached; a visitor whose session was started by older code starts over. Times are stored in UTC and shown in the visitor's browser time zone (`aheadly/timefmt.py`, `st.context.timezone`). | After PR #1 the live site crashed with `AttributeError: per_visitor_data` until it was rebooted, because a cached `Settings` built by the old code met the new code. Settings showed 15:03 for 10:03 in New York, the server's UTC time. |
| 24 | The database upgrades itself: `schema.sql` is version 0 and `Repository.MIGRATIONS` lists numbered upgrades, tracked with `PRAGMA user_version`. Upgrade 1 adds a business profile (JSON, merged on save), where planned items came from and how sure we are (`status`, `certainty`, `likelihood`, `category`, `match_key`, `end_date`, `user_edited`, `paused`), transaction links (`scheduled_item_id`, `category_source`, `is_internal_transfer`), account `kind` and `currency`, `forecast_runs.chance_below_line`, and the tables `payee_rules`, `insights` and `uploaded_files`. The owner's time zone (from the browser) is kept in the profile and decides what "today" is. | Roadmap 1.4: Phase 2 needs these fields, and `CREATE TABLE IF NOT EXISTS` never adds a column to an existing file (a local database, or a saved file loaded later). Insights get their own table because `alerts.type` only allows `shortfall` and `idle_cash`. On Streamlit Cloud the server's date is UTC, so after about 7 pm in New York "today" was already tomorrow. |
| 25 | Six test businesses with answer keys (`tests/businesses/`) were made in a separate chat that never saw the code, from a written brief, by a generator script kept outside the repo (`../aheadly-test-data/test_businesses/`). `tests/test_businesses.py` runs every business through the real app and compares it with its key; anything not built yet is a strict expected failure listed in `PENDING` with its roadmap item, and a scorecard is printed after every run. The businesses and keys are never edited to make a check pass. | Roadmap 1.1 and 1.2. Test data written by whoever writes the code tends to fit the code; independent data is the honest check (like an auditor's own samples). It immediately found reading bugs the code's own tests missed (#26). |
| 26 | Bank files are read the way banks actually export them: comma, semicolon or tab separated; UTF-8 or Windows-1252; preamble lines above the header skipped; Spanish month names (ene, abr, ago, dic…); headers matched without accents and by their first word (Fecha Movimiento, Saldo Disponible, Monto, Detalle); Excel number cells used as they are; a garbled amount such as `8#0` is unreadable instead of becoming 80; an unreadable line no longer counts as a balance break (its Balance carries the check on). | Found by the test businesses: semicolon files and Windows-encoded files didn't open at all, preamble lines hid the header, and the café lost a third of its lines to Spanish month names. |
| 27 | The owner can upload several statements at once (`AppCore.connect_files`). A statement that shares transactions with an account already uploaded is another period of that account (its balance comes from the newest file); any other file is a new account. A credit card statement (an owed-type balance header such as "Balance owed" / "Saldo adeudado", or English "Charges") becomes a `card` account whose balance is stored negative and is not counted as cash. Money out of one uploaded account and the same amount into another within 3 days is a transfer between the owner's own accounts (`aheadly/core/transfers.py`): both sides are flagged `is_internal_transfer` and left out of the forecast's history and of money in/out; paying the card from the bank is flagged the same way with category `card_payment`, so card purchases count as spending once. Money sent to an account that wasn't uploaded (the owner's personal account) stays real money out. | Roadmap 2.1. The test businesses showed the bakery's two overlapping statements being added up as two accounts ($10,960 + $8,200), the hardware store's card statement not opening, and transfers between accounts that would look like income and spending. |
| 28 | "Try an example business" (roadmap 1.5) loads Panadería La Esquina from `aheadly/examples/panaderia-la-esquina/`: copies of that test business's two statements, read through the same upload path as an owner's files (`AppCore.load_example` → `connect_files`), plus the one-off payments its owner knows about (from its answer key) in `example.json`. A test checks the copies stay identical to `tests/businesses/`. The profile records `example`, and the app says it is an example instead of the usual old-statement warning. Its dates are not shifted to today. | Anyone (the class, a teacher, a visitor) can see the whole app in one click without making files. Reusing a test business means the example is one the automatic checks already look at, and going through `connect_files` means it tests the real import. Shifting dates to today would move the December story into January and break the weekday patterns, so the example stays fixed at Nov 11, 2026 and says so. |
| 29 | Categories (roadmap 2.2) come from rules, not a language model: `aheadly/ai/categorizer.py`, run after every upload. First match wins: the owner's answers (`payee_rules`, set with `AppCore.set_payee_rule` / `answer_payee`), moves between the owner's own accounts, a category the file itself carried, keyword rules for Colombian and US bank wording, then defaults (money in = sales, a PSE payment = supplier, else other). An owner's answer that a line is their own money also takes it out of income and spending. The zero-shot model in the roadmap (`bart-large-mnli`) is left out. The What-if "change sales" now uses the business's real average weekly sales (last 8 weeks) instead of a fixed $5,500. | Bank lines are short codes ("PAGO PILA APORTES", "GMF 4X1000") that rules read reliably and explainably; the model would add about 2 GB (torch) to the Streamlit Cloud app for little gain on such text. Honest limit: the keyword list was written looking at the six test businesses, so their scorecard flatters it (after the owner's answers, 632 of 644 monthly category totals match within 5%; 4 misses are lines the files show as unreadable, 8 are a hardware store's Homecenter purchases, which are supplies for it and "other" for the others). On the sample export, which the rules were not written from, payroll, rent, utilities and sales are right, but "Flour and dairy" and "Oven maintenance" fall to other. Those are what the onboarding questions (2.7) ask about; there, the connected language model suggests a category for the few payees left in "other" (names only, the owner confirms), instead of a local model. |
| 30 | Recurring payments and income (roadmap 2.3, `aheadly/ai/recurring.py`) are found by rules on the dates themselves: lines are grouped by payee (the description in plain form; numbers masked only when they change from line to line) and direction, and each group gets the calendar rule that fits: some weekdays every week (daily / twice a week / weekly), every two weeks, a day of the month or its last business day, twice a month, every 2, 3, 6 or 12 months, or, when the day drifts later each month, the typical gap. Weekends move to the next business day, except payroll (the business day before), unless the payee's own history shows otherwise; public holidays are not known. Monthly-or-rarer items and fixed-amount weekly ones become scheduled items (`status='detected'`, `source='statement'`) on their real dates, and their past lines are linked to them (`transactions.scheduled_item_id`) and left out of what the model learns from. Daily and weekly flows whose amount varies (card sales, weekly supplier orders) stay in that history. A payment the owner already listed that matches a detected one within 10 days and 40% of the amount (30% until 2.5: an insurer's payments vary more) (the quarterly flour order, an insurer's claim) replaces it. A plan that moves or removes a detected item marks it `user_edited`, and later uploads leave it alone. | The forecast model only knows weekly rhythm, so it spread rent and payroll over every day; on their own dates the dips land where they really are (the café's December bonus is what takes it under its line on Dec 18). Scheduling the variable daily flows instead would make the forecast look far more certain than it is, because its uncertainty band comes from them. Considered and left out: shifting each coming month by how the same month differed last year. With one year of data it is too noisy (it got the bakery's December right but invented one for the café); the owner's "busy months" answer (2.7) is the honest source. Until then the bakery's December check waits (PENDING). |
| 31 | "Just say it" (roadmap 2.4, `aheadly/ai/plan_text.py`): the owner writes what's coming in their own words, on Accounts or in the chat, and gets proposed plan items to check and edit; nothing is saved until they press Add (`AppCore.parse_plan_text` reads, `AppCore.add_plan_items` saves). The connected model reads the text through the `propose_plan_items` tool; the offline rules read it with the stub provider and whenever the model fails or finds nothing. Code checks every item either way: a positive amount the owner actually wrote (a model's invented amount is flagged), a date from today on, in or out, how often; what's missing is asked ("How much?", "When?"), never guessed. In the chat the tool only proposes; the card under the answer has the Add button. | Owners describe their plans in sentences, not files. The language model is good at reading those, but a wrong amount or date in a cash forecast is costly, so the model only proposes and the owner confirms, and code verifies the amounts come from the owner's words (the same rule as "numbers come from code, the model writes words"). The offline rules keep the feature working without a key and in tests; they read every sentence the six test owners wrote. |
| 32 | Owner's files (roadmap 2.5, `aheadly/data/connectors/owner_files.py`): any CSV or Excel the owner keeps is one of five kinds (upcoming payments, money customers owe, employee list, accounting ledger, inventory), told apart by its column titles in Spanish or English (header row found below any title lines). Only upcoming payments and receivables add money to the forecast; the employee list is compared with the payroll found in the statement (it never adds pay, so payroll can't count twice); the ledger and inventory are summaries. A list of all-positive amounts with no in/out column is a list of payments; with both signs, minus is money out (the old upcoming-payments format still works). Overdue invoices up to 60 days late are a maybe two weeks from today; older ones are listed, not counted. When the titles don't say, the connected model sees the titles only (never a value) and names the kind and which title is which; titles it names must exist. Every file is previewed and used only when the owner presses Use; payments already in the plan (same sign, amount within 1%, date within 3 days) aren't added again. Files unlike the test businesses' ones (tried on purpose): the sheet with the data is found among several; total and subtotal rows are left out; a file with no title row keeps its first row and names the columns by position; when titles don't say what a column is, the owner points at it (a dropdown of the file's own titles, with a sample value each), so nothing ends in a dead end without the model; rows whose date or amount can't be read are counted and shown; a bank statement put here is pointed out. Not built yet: "what if I hire" from the employee list, ledger lines as categories, restock suggestions from the inventory, budgets laid out by month (nice to have). | Owners keep these files in their own layouts; reading the titles is reliable and explainable, and the model only helps when they're unusual, without seeing personal data. A receivables file and the insurer's payments found in the statement are the same money, so a listed payment replaces a detected one that matches (DECISIONS #30, widened to 40% here). |
